# Архитектура InsureTech: Ответы на вопросы

## 1. Стратегия масштабирования и отказоустойчивости

### Горизонтальное vs Вертикальное масштабирование

**Горизонтальное масштабирование (основная стратегия):**
- **Kubernetes HPA** во всех зонах (CPU 80%, Memory 85%)
- **Auto Scaling Groups** для Kubernetes нод
- **Распределенные сервисы** с 2+ pods в каждой зоне
- **Балансировка нагрузки** между 5 зонами доступности

**Вертикальное масштабирование (вспомогательное):**
-  **Только для PostgreSQL** при значительном росте данных
-  **Redis Cluster** вертикально при необходимости
-  **Ограниченное применение** из-за downtime при масштабировании

**Эффективность:** **Горизонтальное масштабирование значительно эффективнее** для данной системы:

| Критерий | Горизонтальное | Вертикальное |
|----------|----------------|--------------|
| Обработка пиковых нагрузок |  250+ RPS |  Ограничено ресурсами сервера |
| Время простоя |  Нулевое |  Требуется перезапуск |
| Cloud-native |  Полное соответствие |  Частичное |
| Независимое масштабирование |  Компоненты независимо |  Вся система |

## 2. Использование дополнительных зон безопасности

**Да, используются дополнительные зоны безопасности:**

### Уровни изоляции:
1. **Региональная изоляция** (Central Russia / Ural)
2. **Зоны доступности** (3 AZ в Region 1, 2 AZ в Region 2)
3. **Сетевые сегменты**:
   - Public Load Balancer (интернет)
   - Regional Load Balancer (внутренний)
   - API Gateway уровень
   - Сервисный уровень
   - База данных (изолированная сеть)

### Дополнительные меры безопасности:
-  **Rate Limiting** 20 RPS/партнер
-  **Circuit Breaker** для предотвращения каскадных сбоев
-  **JWT Validation** на каждом API Gateway
-  **Health Checks** на всех уровнях
-  **SSL Termination** на Global Load Balancer

## 3. Тип кластеров: независимые vs растянутые

### Принятое решение: **НЕЗАВИСИМЫЕ КЛАСТЕРЫ**

#### Kubernetes кластеры:
- **Независимый кластер в каждой зоне доступности**
- **Автономное управление и масштабирование**
- **Изоляция сбоев**

#### PostgreSQL кластер:
- **Растянутый кластер** (Region 1) с Patroni + ETCD
- **Синхронные реплики** во всех 3 зонах
- **Автоматический failover**

### Обоснование выбора:

#### Почему независимые Kubernetes кластеры:
1. **Изоляция сбоев** - проблемы в одной зоне не влияют на другие
2. **Локальное управление** - каждый кластер оптимизирован под свою зону
3. **Снижение сетевой задержки** - минимизация трафика vt;le зонами
4. **Упрощение обслуживания** - можно обновлять кластеры независимо

#### Почему растянутый PostgreSQL кластер:
1. **Согласованность данных** - синхронная репликация обеспечивает zero data loss
2. **Автоматический failover** - Patroni обеспечивает высокую доступность
3. **Единая точка управления** - проще администрировать один распределенный кластер
4. **Требования RPO** - синхронная репликация обеспечивает RPO = 0

## 5. Фейловер-стратегия

### Active-Active с приоритетом региона:
- **Primary Region** (Central Russia) - обработка записи и чтения
- **Secondary Region** (Ural) - чтение из async реплики
- **Автоматический failover** при недоступности Primary Region
- **Время восстановления** < 5 минут (соответствует RTO 45 мин.)

### Сценарии восстановления:
1. **Сбой зоны** - трафик перенаправляется в другие зоны того же региона
2. **Сбой региона** - Global LB перенаправляет трафик в другой регион
3. **Сбой базы данных** - автоматическое переключение на синхронную реплику

## 6. Обеспечение RTO 45 мин. и RPO 15 мин.

### RTO (Recovery Time Objective):
- **Автоматический failover** < 5 мин.
- **Health Checks** обнаруживают сбои за 15-30 секунд
- **Global LB** перенаправляет трафик мгновенно

### RPO (Recovery Point Objective):
- **Синхронная репликация** в Region 1 (RPO = 0)
- **Асинхронная репликация** в Region 2 (~15 мин. lag)
- **WAL-G continuous archiving** с PITR 15 мин.
- **Полные бэкапы** каждые 4 часа
