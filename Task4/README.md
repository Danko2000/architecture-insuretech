## Хранилище osago-aggregator:

Да, требуется отдельное хранилище osago-agg-db (PostgreSQL) для хранения заявок ОСАГО, статусов по страховым компаниям и полученных предложений. Это необходимо для корректной корреляции ответов, восстановления после перезапуска сервисов и соблюдения дедлайна 60 секунд.

## API osago-aggregator для core-app:

Внутренний REST-API:

**POST /api/osago/quotes** – запуск обработки заявки (возвращает osagoRequestId).

**GET /api/osago/quotes/{osagoRequestId}** – получение текущего состояния и списка предложений.
(опционально GET /api/osago/quotes/{id}/stream для стриминга).

## Средство интеграции core-app ↔ osago-aggregator:
REST через Kubernetes Service (ClusterIP).
Над вызовами применены паттерны Timeout + Retry + Circuit Breaker.

## API для веб-приложения:

POST /api/osago/quotes – создание заявки ОСАГО; возвращает идентификатор заявки.

GET /api/osago/quotes/{coreOsagoId} или WebSocket/SSE-канал – получение/стриминг предложений.

## Средство интеграции веб-приложение ↔ core-app:
REST + (опционально) WebSocket/SSE. REST – для создания заявок, WebSocket/SSE – для получения предложений по мере прихода.

## Паттерны отказоустойчивости:

**Rate Limiting** – на входящем B2B-трафике и на исходящем трафике к страховым компаниям.

**Timeout** – для всех внешних запросов (особенно к страховым компаниям).

**Retry** – с ограничением количества и backoff для временных ошибок.

**Circuit Breaker** – между core-app и osago-aggregator, а также между osago-aggregator и страховыми компаниями.

## Учитывание нескольких экземпляров сервисов:
Сервисы core-app и osago-aggregator масштабируются горизонтально.\
Основа — stateless-логика, общий Postgres osago-agg-db,\
идемпотентность запросов и корректная корреляция по идентификаторам заявок.
